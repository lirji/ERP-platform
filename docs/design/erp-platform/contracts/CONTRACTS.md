## 1. API 与 Event 版本

### 1.1 路径

```
/api/v1/{context}/{resource}
```

`{context}` 取限界上下文短名：`iam` `masterdata` `inventory` `purchase` `sales` `finance` `approval` `document` `reporting` `numbering`。

> **对 `ENGINEERING_CONVENTIONS.md` §2 的修正**：该文档写的是 `/api/{context}/{resource}`（v1 隐式、v2 显式）。
> 本契约改为**版本始终显式**。隐式 v1 会让"第一次破坏性变更"成为一次路径形态的突变，
> 客户端要同时处理两种形状；显式版本从第一天起形状一致。该约定以本契约为准。

### 1.2 兼容规则

| 变更 | 兼容性 | 允许在 v1 内做 |
|---|---|---|
| 新增可选响应字段 | 兼容 | ✅ |
| 新增可选请求字段（有安全默认） | 兼容 | ✅ |
| 新增枚举值 | **半兼容** | ⚠️ 仅当消费方已按"未知值忽略/降级"实现；否则算破坏 |
| 字段改名 / 改类型 / 改语义 | 破坏 | ❌ 走 v2 |
| 删除字段 | 破坏 | ❌ 先弃用标注，v2 才移除 |
| 收紧校验（如新增必填） | 破坏 | ❌ 走 v2 |

**枚举消费规则（强制）**：所有消费方对未知枚举值必须能降级处理，不得抛异常中断。
这让"新增枚举值"保持为加法变更——否则每加一个单据状态都要升版本。

### 1.3 Event 版本

事件契约见 [`EVENT_CATALOG.md`](EVENT_CATALOG.md)。事件名本身带版本：`PurchaseReceiptPosted.v1`。
事件的兼容规则与 §1.2 相同；**事件一旦发布，其 payload 字段语义不可改**——历史事件在 Outbox 与审计中长期存在，改语义会让重放产生错误结果。

## 2. 错误语义

### 2.1 响应结构

```json
{
  "code": "ERP-INV-1001",
  "message": "可用库存不足",
  "traceId": "3f9d4afa548a4641922d2849ff667cef",
  "details": { "skuCode": "SKU-001", "required": "10", "available": "3" }
}
```

- `code` 必填，取值见 [`ERROR_CODES.md`](ERROR_CODES.md)；
- `message` 面向**最终用户**，中文，不含技术细节；
- `traceId` 必填，与响应头 `X-Trace-Id` 相同；
- `details` 可选，结构化补充，**不得包含 SQL、堆栈、内部类名、其他租户数据**。

### 2.2 HTTP 状态码映射

| 状态 | 含义 | 何时 |
|---|---|---|
| 400 | 请求本身不合法 | 参数校验失败、枚举非法 |
| 401 | 未认证 | 无 token / token 失效 |
| 403 | 已认证但无权 | 功能权限或数据权限不允许 |
| 404 | 资源不存在**或无权访问** | 见下方说明 |
| 409 | 与当前状态冲突 | 非法状态迁移、乐观锁冲突、唯一约束冲突 |
| 422 | 业务规则不满足 | 库存不足、超收超限、信用超额 |
| 500 | 系统异常 | 不可预期；**不得泄漏内部细节** |

> **404 vs 403 的选择**：当资源存在但**不在调用方数据权限范围内**时返回 **404 而不是 403**。
> 403 会泄漏"这个 ID 存在"这一事实，在多租户系统里等于跨租户存在性探测。
> 仅当资源在范围内、但调用方缺少**功能权限**时才返回 403。

### 2.3 400 与 422 的边界

- **400**：不看业务数据就能判定不合法（缺字段、类型错、枚举不存在）。
- **422**：请求格式完全合法，是**业务规则**拒绝（库存不足、超额付款）。

二者混用会让前端无法区分"用户填错了"与"业务上不允许"，前者应高亮字段，后者应给业务提示。

## 3. 时间与时区

| 场景 | 类型 | 约定 |
|---|---|---|
| 系统时刻（创建/修改/过账时间） | `TIMESTAMPTZ` / ISO-8601 带偏移 | 存 UTC；API 返回 `2026-09-21T10:41:33.925+08:00` |
| 业务日期（单据日期、账期） | `DATE` / `yyyy-MM-dd` | **无时区**。单据日期是业务事实，不随查看者时区变化 |
| 租户时区 | `iam_tenant.timezone`，IANA 名（`Asia/Shanghai`） | 业务日期的归属按**租户时区**计算，不按服务器时区 |

**为什么把二者分开**：把单据日期做成带时区的时刻，会导致同一张单在不同时区的用户看来属于不同账期——
这是财务对账里极难排查的一类错误。业务日期一旦确定就不再换算。

**服务器时区**：应用与数据库容器统一 `Asia/Shanghai`（见 `deploy/compose.yaml`），但代码**不得依赖**
系统默认时区，所有日期归属计算必须显式传入租户时区。

## 4. 数据唯一性与完整性

### 4.1 唯一性一律带租户维度

任何业务唯一约束都必须包含 `tenant_id`：

```sql
-- 正确：租户内唯一
CREATE UNIQUE INDEX uk_md_product_code ON md_product (tenant_id, code);
-- 错误：全局唯一 —— 会让 A 租户占用 B 租户的编码
```

### 4.2 「未取消才唯一」用部分唯一索引

```sql
CREATE UNIQUE INDEX uk_pur_order_no ON pur_order (tenant_id, order_no)
    WHERE status <> 'CANCELLED';
```

这是选择 PostgreSQL 的直接理由之一（`ADR-001`）。

### 4.3 完整性约束放在数据库

应用层校验用于**给出友好错误**，数据库约束用于**保证正确性**。并发下"先查后写"不成立，
因此凡是不变量都必须有对应的唯一索引或检查约束（开发规范 §设计 8）。

### 4.4 金额与数量

| 项 | 类型 | 约定 |
|---|---|---|
| 金额 | `NUMERIC(18,4)` | 禁止浮点；MVP 单一本位币（`A-08`），字段仍带 `currency` |
| 数量 | `NUMERIC(18,6)` | 精度 6 位以容纳换算后的小数 |
| 单价 | `NUMERIC(18,6)` | 高于金额精度，避免 单价×数量 先舍入再相乘 |

**舍入规则**：金额计算一律 `HALF_UP` 保留 4 位；对外展示由前端按币种小数位格式化，**不在后端预先舍入**。

## 5. 失败与 timeout 语义

| 层 | 超时 | 失败语义 |
|---|---|---|
| HTTP 入站 | 无显式上限（内部系统） | — |
| 数据库语句 | 30s（报表 60s） | 超时 → 500 + `ERP-SYS-0003` |
| 数据库连接获取 | 10s | 超时 → 500 + `ERP-SYS-0002` |
| 外部系统（Casdoor 等） | 5s 连接 / 10s 读 | 失败 → 502 + `ERP-SYS-0004`，**不得静默降级为"认证通过"** |

**未知结果（timeout）的处理原则**：超时意味着**结果未知**，不等于失败。
对有副作用的操作，调用方必须凭幂等键重试或查询确认，**不得假定未生效**（开发规范 §设计 9）。

## 6. UI 与真实 API 状态一致性

- 前端**不得**把"请求已受理"呈现为"业务已完成"。
- 异步动作（审批提交、Outbox 驱动的下游单据生成）必须返回可查询的状态，
  前端据此显示 `处理中`，而不是乐观地显示成功。
- 这条在 P8 接入 `workflow-platform` 时尤其重要：引擎侧返回 202 不代表审批完成
  （见 ROADMAP P8 出口条件 ②）。

## 7. 租户（Conditional：启用）

- `tenantId` **只从 `AccessContext` 取**，即来自已验证的身份令牌。
- **禁止**从请求体、查询参数或请求头接受 `tenantId`——那等于把越权做成了一个入参。
- 所有业务表含 `tenant_id`，所有查询强制注入过滤条件（MyBatis 拦截器，P1.4 实现）。
- 违反由 P1 出口条件的 SQL 断言检测：断言**生成的 SQL** 中确实出现租户条件。

## 8. 幂等（Conditional：启用）

- 写操作接口接受可选请求头 `Idempotency-Key`（调用方生成，UUID）。
- 作用域：`(tenant_id, endpoint, idempotency_key)`。
- 重复请求返回**首次结果**（含相同 HTTP 状态），不重复产生副作用。
- **兜底必须在数据库**：业务级幂等键（如 `(tenant_id, source_doc_type, source_doc_id)`）
  建唯一索引；`Idempotency-Key` 是调用方便利，不是正确性保证。
- 事件消费幂等由**消费方**保证，不依赖投递方只发一次。

## 9. 乐观锁（Conditional：启用）

- 有状态流转的聚合根带 `version BIGINT NOT NULL DEFAULT 0`。
- 更新语句形如 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`。
- **必须检查影响行数**：0 行 = 冲突 → 409 + `ERP-SYS-0005`。把 0 行当成功是本项目明确禁止的写法。

## 10. 分页（Conditional：启用）

```
GET /api/v1/{context}/{resource}?page=1&size=20&sort=createdAt,desc
```

- `page` 从 **1** 起；`size` 默认 20，**上限 200**，超出返回 400。
- 响应：`{ "list": [...], "total": 1234, "page": 1, "size": 20 }`。
- `sort` 字段走**服务端允许列表**，禁止把用户输入拼进 `ORDER BY`（开发规范 §7）。
- 排序必须**稳定**：任何排序都隐式追加 `, id ASC` 作为最后一个排序键，否则等值行在翻页时会重复或丢失。

## 11. 审计（Conditional：启用）

每个写操作产生一条审计记录，字段见 `EVENT_CATALOG.md` 的 `AuditRecord`。
审计在**写入路径**上拦截（AOP），不是事后补记——这是把 CAP-P09 从提示词 Phase 11 提前到 P1 的原因。
