# P6 应收应付与核销内部契约

承接 ROADMAP P6 / DOMAIN_MAP 的既有业务不变量，范围为模块内用例与真实数据库闭环；不发起真实银行付款、不新增 HTTP 端点或生产部署。

## 数据与用例

- AR/AP 分别使用 `fin_account_receivable` / `fin_account_payable`，收付款分别使用 `fin_receipt` / `fin_payment`。同一 SettlementService 共用核销算法。
- 金额 NUMERIC(18,4)、HALF_UP 四位，币种来自上游生成事件时读取的启用本位币（md_currency）。禁止默认猜测币种。当前订单价即本位币单价，不新增税额/汇率模型。
- v2 出入库事件携带来源单据、订单、主体、往来单位、金额、币种、组织和操作人。金额由本次收发数量乘订单单价汇总，累计差额按每行累计金额之差计算，防止分批舍入导致总额漂移。
- 财务消费者仅依赖事件，不跨模块查表；来源唯一键保证重复事件一张 AR/AP。v1 历史事件只保留已有关系图语义，缺金额不可猜；存量单据补算由来源模块另行产生 v2，不能伪称历史账已齐。
- `recordCash` 记录针对一张往来单的收款/付款：金额为正，累计不超过原金额；commandId 在租户和类型内唯一，同键同内容返回原记录，不同内容拒绝。
- `apply` 同事务增加往来单与收付款单的已核销金额；两端不得超额，同一对单据只允许一笔有效核销。锁顺序固定为往来单→收付款单。
- `reverse` 必须给原因；同事务退回两端已核销金额，并新增引用原记录的负金额流水。原记录保留，标记已反核销；重复反核销拒绝，反核销后允许重新核销。
- 反核销不撤销已经发生的收付款事实，paid_amount 不回退；资金退款不属于本期。
- 财务单沿来源单与订单建立 Outbox 关系事件，收付款及核销记录保留操作者与时间。

## 可靠投递

财务事件处理在独立事务中执行，失败必须向 Outbox 抛出；业务提交与 PUBLISHED 之间崩溃可重放，由唯一约束幂等。轮询采用有界批次和既有重试上限，新增本地调度用于持续消费；测试默认关闭后台线程以保持隔离。

## 验收

P6 七条 ROADMAP 出口、重复及并发事件、不超额/重复核销、反核销并发、同键重试、跨租户及币种拒绝、事件失败可重试、来源双向追溯。Outbox P95 记录本地实际样本，不宣称生产 SLO。

## 信用与财务边界

Sales 保留未取消订单的累计信用占用本金；Finance 通过 kernel 的 `SettledCreditQuery` 提供客户应收核销净额（正向减反向）。硬校验及展示的实际占用为本金减核销净额，直接读取权威财务数据，不等待事件投影。符合 CONSISTENCY_MODEL §7 的硬校验要求，保持编译期模块依赖矩阵；不存在 Sales 直接查询 fin_* 表或 Finance 写 sal_* 表。


## 本地运行准备

- 运行已有 PostgreSQL，并对目标环境执行正常 Flyway 迁移到 V90；本轮仅迁移了隔离 erp_it 库。
- 每个业务租户须维护启用本位币，以及 PO/IN/SO/OUT/AR/AP/PAY/RCV 编号规则；缺配置明确失败。测试 fixture 会在各自专属租户中写入这些配置。
- `erp.outbox.scheduling-enabled` 默认 true；`erp.outbox.poll-interval-ms` 默认 1000，允许 100–60000ms。
- `mvn clean verify` 执行全量回归；`FinanceSettlementE2EIT` 的测试数据真实写入隔离库，可重复运行，各 fixture 仅清理自身租户。
- 历史 v1 缺财务载荷，现有业务存量不自动补账。上线前需单独完成生产 OIDC、入口权限、币种/编号配置及存量评估。
