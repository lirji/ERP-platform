# Consistency & Idempotency Model

> Owner: `backend-architecture-design`
> 选择顺序：**最弱但足够**。① 本地事务 → ② 同库 Outbox → ③ 跨边界消息 + 幂等/Inbox/补偿 → ④ Saga → ⑤ 分布式事务（只有能说明 ①–④ 为何不够时）。

## 1. 场景 → 一致性范围 → 手段 → 失败与恢复

| # | 业务场景 | 一致性范围 | 手段 | 失败与恢复 |
|---|---|---|---|---|
| 1 | 采购收货过账（更新收货累计量 + 库存余额 + 库存流水 + 单据关系 outbox） | **Strong**（单进程单库） | **本地事务** + 唯一键幂等 | 失败整体回滚；重放同 `commandId` 被唯一键拒绝，返回首次结果 |
| 2 | 销售出库过账（扣减 onHand + 消耗 reserved + 流水） | **Strong** | **本地事务** + 行级锁（按稳定桶键排序加锁避免死锁） | 同上；死锁只对整个幂等用例有界重试 |
| 3 | 库存预占 / 释放 | **Strong** | 本地事务 + `(source_doc_type, source_line_id)` 唯一键 | 重复预占返回原预占；释放不超过未消耗量由领域校验 |
| 4 | 过账 → 生成应付/应收 | **Eventual**（≤ 60s，NFR-08） | **同库事务性 Outbox** + 进程内可靠投递 + 消费端唯一键 INV-06 | 投递失败按退避重试；超过上限进 `erp_outbox_dead`，有运维补发入口；**唯一键保证重复投递不产生第二张单** |
| 5 | 过账/单据事件 → 单据关系图 + 审计 | **Eventual** | 同 4 | 登记失败**不影响主事务成败判定**，但必须可补；有对账脚本比对「有流水无 link」 |
| 6 | 业务提交 → 审批 → 业务状态迁移 | **Eventual** | ApprovalPort（MVP 进程内同事务提交；Phase 8 改 Kafka） | **审批实例状态不是业务状态权威**；`ApprovalCompleted` 事件带 `(businessType, businessId, decisionId)`，业务侧按 `decisionId` 幂等迁移 |
| 7 | 应收变化 → 客户信用占用 | **Eventual** | 事件 | 下单时的**硬校验直接读 BC-6 当前值**，不读可能过期的投影（提示词一致性要求；缓存不得承担关键决策） |
| 8 | 业务事件 → 报表读模型 | **Eventual** | 事件投影 | 投影可从权威数据全量重建 |
| 9 | 仓间调拨（调出 → 在途 → 调入） | **Strong**（单库内）| 两次过账 + `in_transit` 中间态，**在途不计入任一仓 onHand** | 未接收的在途可撤回；企业维度守恒 INV-08 由对账脚本每日校验 |
| 10 | 与 `workflow-platform` 的审批（Phase 8） | **Cross-System Eventual** | Outbox → Kafka → 对方 inbox；回执 → 本方 inbox | 结果未知不得当失败；必须有对账（比对 ERP 待审实例 vs 平台实例） |
| 11 | 与 Casdoor 的登录 | **Cross-System** | OIDC 授权码，无本地事务参与 | 认证失败即登录失败，无补偿需求 |

## 2. 明确不使用的手段及理由

| 手段 | 不用的理由 |
|---|---|
| **TCC** | 资源方与消费方在**同一进程同一数据库**，本地事务已提供更强保证。TCC 只在资源方支持 Try/Confirm/Cancel 且需要严格隔离时考虑。`wms-platform` 用 Seata TCC 是因为**跨仓跨进程**，本项目不具备该前提 |
| **Saga** | 当前没有跨服务的长事务 |
| **分布式锁** | 单进程内行级锁 + 乐观锁已足够；引入 Redis 锁反而增加"锁丢失"这一新失败模式 |
| **MQ（MVP）** | 无跨进程异步协作（见 `DATA_ARCHITECTURE.md`） |
| **双写（DB + 外部系统，无恢复故事）** | 明确禁止 |

## 3. 幂等策略对照表（提示词第十九章）

| 手段 | 解决什么问题 | 本项目用在哪 |
|---|---|---|
| **唯一约束** | 防止同一业务事实产生两条记录 | 库存流水 `(source_doc_type, source_doc_id, source_line_id, direction)`；AR/AP `(source_doc_type, source_doc_id)`；核销 `(bill, payment, reversal_of)` |
| **幂等 Key** | 客户端重试不产生第二次效果 | 所有写接口接受 `Idempotency-Key`，映射到服务端 `operation_id`；`erp_idempotency` 表记录 `(tenant_id, key) → 首次结果` |
| **CAS / Version（乐观锁）** | 并发修改只有一个成功 | 库存余额、单据头、AR/AP。**更新必须检查影响行数，影响 0 行不得当成功**（全局开发规范 §8） |
| **Outbox** | 保证"提交后一定触发"的异步副作用 | 过账 → AR/AP、事件 → 单据图/审计/读模型 |
| **Inbox** | 跨进程重复消费去重 | Phase 8 接入 `workflow-platform` 时启用；MVP 不需要 |
| **Retry** | 瞬时故障恢复 | 必须有截止时间、次数上限、退避与抖动；**只对可重试且有幂等保障的动作重试** |
| **Compensation** | 已提交效果的业务补偿 | 反核销单、退货单、库存调整单——**都是新单据**，不是"回滚镜像" |
| **Reconciliation（对账）** | 结果未知与长期漂移的兜底 | 每日：库存余额 vs 流水累计（INV-01）；企业数量守恒（INV-08）；有流水无 document_link；Outbox 积压 |

## 4. 并发写的具体协议（库存）

所有库存入口共用同一锁顺序，避免死锁：

```text
1. 先按稳定桶键排序（tenant, company, warehouse, location, sku, batch）
2. 再锁单据头（乐观锁 version）
3. 最后锁余额行（SELECT ... FOR UPDATE，按上一步的排序逐个加锁）
```

- 初始化空库存桶由**数据库唯一键仲裁**：插入冲突后重新读取，**不能仅在 Java 中查不存在就插入**。
- 冻结/质量/效期是**资格约束**，参与 `available` 的计算，**不作为另一个数量从余额机械相减**（否则会重复扣减）。
- `available` 是计算值，数据库中**不存**可随意改写的"可用总数"字段。

## 5. 验证方式（进入 Gate 的证据要求）

以下必须由**集成测试**（真实 PostgreSQL，Testcontainers）证明，不接受纯 Mock：

| 不变量 | 测试 |
|---|---|
| INV-01 | 随机 1000 次过账后，余额 == 流水代数和 |
| INV-02 | 并发 50 线程扣减同一桶，无负库存、无超卖 |
| INV-04 | 同一来源单据行过账 10 次，库存效果只发生一次 |
| INV-05 | 超收超过配置比例被拒；关闭后不可再收 |
| INV-06 | 同一入库单触发 10 次事件，只产生一张应付 |
| INV-07 | 超额核销被拒；重复核销被拒；反核销后可再核销 |
| INV-08 | 调拨全流程后企业维度数量守恒 |
| INV-10 | 非法状态迁移抛领域异常；并发迁移只有一个成功（另一个收到乐观锁冲突，**不得当成功**） |
