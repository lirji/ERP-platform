# Architecture Evolution

> Owner: `backend-architecture-design`
> **没有触发条件就停在当前阶段。** 每个阶段的进入条件必须是可观察的事实，不是"感觉该拆了"。

```text
Stage 1 Modular Monolith  ──►  Stage 2 读写分离 + 读模型  ──►  Stage 3 选择性服务抽取  ──►  Stage 4 多服务
     (MVP，当前)                    (触发时)                       (触发时)                   (可能永不到达)
```

| 阶段 | 形态 | 进入触发条件（可观察） | 变化内容 | 前置条件 | 可回退 |
|---|---|---|---|---|---|
| **Stage 1** | 单进程 `erp-app` + 单 PostgreSQL；9 个上下文为 Maven 模块 | — （当前） | — | — | — |
| **Stage 2** | 增加只读副本 + 报表读模型独立表（仍单进程） | 报表查询 P95 > 3s **且** 其 CPU 占比 > 30%；或月末结账期间业务写入 P95 劣化 > 2× | 报表走只读副本；`rpt_*` 读模型由事件投影 | 事件投影已可重建；读模型重建脚本已验证 | 可（停用读模型，回落实时查询） |
| **Stage 3** | 抽出 1–2 个进程（**候选按优先级**：① Reporting ② Approval ③ Inventory） | 满足**任一**：(a) 某上下文需要独立发布节奏（每周 ≥ 2 次而其他模块 ≤ 1 次）；(b) 某上下文持续负载超过单体容量 50%；(c) 出现第二个团队独立负责某上下文；(d) 合规要求故障域隔离 | 按已有端口抽进程；跨进程改为 REST/事件 + 幂等 + 对账 | 端口已存在且无跨模块表访问（ArchUnit 已保证）；已有分布式追踪；已有对账脚本 | 部分（数据已分库则回退昂贵） |
| **Stage 4** | 多服务 | 同时出现多团队 + 多故障域 + 独立扩缩需求 | 进一步拆分 | Stage 3 的运维故事已被验证 | 否 |

## 抽取优先级的理由

| 候选 | 为什么排这个位置 |
|---|---|
| ① Reporting (BC-9) | **最容易**：只读、无写模型、与业务是 Separate Ways，抽走不影响任何不变量 |
| ② Approval (BC-7) | 次容易：已经是端口 + 适配器结构；且如果接了 `workflow-platform`，审批本来就已在进程外 |
| ③ Inventory (BC-3) | **最难，最后考虑**：抽走会把 INV-01/03/04（过账与单据同事务）变成分布式一致性问题，需要 Outbox + 对账 + 可能的补偿。只有在容量确实成为瓶颈时才做 |
| ❌ Procurement / Sales / AR-AP | **不建议单独抽取**：它们与 Inventory 的强一致耦合最深，抽出后收益最小、代价最大 |

## Stage 1 就要守住的约束（否则以后拆不动）

这五条在 Phase 0 的工程基线中落地并由 ArchUnit 强制：

1. 模块依赖方向单向：`kernel ← platform ← master-data ← core-business ← app`，禁止反向与环。
2. 跨模块**禁止**访问对方的表（包括只读 SELECT）。
3. 每模块独立表前缀（`iam_` `md_` `inv_` `pur_` `sal_` `fin_` `apr_` `doc_` `rpt_`）与独立 Flyway 迁移目录。
4. 跨模块协作只经应用服务接口或领域事件；领域对象不跨模块传递（用 DTO / 事件契约）。
5. 不在模块之间共享 JPA/MyBatis 实体类；共享的只有 `erp-kernel` 里的值对象与错误码。
