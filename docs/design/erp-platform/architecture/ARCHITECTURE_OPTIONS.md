# Architecture Options & Decision

> Owner: `backend-architecture-design`
> 提示词第十四章要求「不要预设必须使用微服务」，先比较 Modular Monolith vs Microservices，给出依据。

## 1. 部署形态候选

| 选项 | 适合 | 前提 | 主要代价 | 本项目评估 |
|---|---|---|---|---|
| **A. Modular Monolith** | 团队小、领域边界仍在学习、强一致需求多、交付周期紧 | 模块边界与数据所有权靠规则和测试守住 | 整体发布；单模块无法单独扩缩 | ✅ 全部前提满足，全部代价可接受 |
| B. Microservices | 多团队独立发布、容量或故障域差异明显、组织边界清晰 | CI/CD、可观测、服务治理、分布式一致性能力到位 | 运维与一致性复杂度显著增加 | ❌ 无任何驱动因素证据 |
| C. SOA / ESB | 企业已有集成总线、需统一对接大量既有系统 | 已有服务治理与契约管理 | 中心化总线易成瓶颈 | ❌ 无既有总线，对接对象只有 3 个 |
| D. Event-Driven Architecture | 业务天然以事件推进、需异步解耦、审计/重放需求 | 事件契约治理、幂等、乱序处理 | 调试与一致性推理更难 | ⚠️ **不作为整体形态**，但在「过账→往来账」「业务→审计/单据图」两处以进程内事件+Outbox 局部采用 |

## 2. 决策驱动因素逐项评估

| 驱动因素 | 事实 / 假设 | 证据类型 | 指向 |
|---|---|---|---|
| 业务复杂度 | 高（9 个上下文、多状态机、强不变量） | USER_REQUIREMENT | 复杂度在**领域**，不在**分布式**。拆进程不降低领域复杂度，只增加一致性成本 → A |
| 团队规模 | 1–5 人（A-07） | BUSINESS_ASSUMPTION | 微服务的收益（独立发布/独立所有权）在单团队下为零 → A |
| 一致性要求 | 强：INV-01/02/05/06/07 多数跨「单据↔库存↔往来账」 | USER_REQUIREMENT | 拆进程会把本地事务变成 Saga/TCC → A |
| 部署能力 | 本地 Docker Compose，无 K8s，无服务网格 | REPOSITORY_EVIDENCE `dev-infra/compose.yaml` | → A |
| 运维能力 | 无独立运维团队 | BUSINESS_ASSUMPTION A-07 | → A |
| 未来规模 | 峰值 ≈45 写/秒（`SYSTEM_VISION.md` 推导） | BUSINESS_ASSUMPTION | 与单库容量差约两个数量级 → A |
| 组织边界 | 单一组织 | BUSINESS_ASSUMPTION | → A |
| 技术能力 | Java 21 / Spring Boot 3.x 熟练（Workspace 内多项目一致） | REPOSITORY_EVIDENCE | 两者皆可 |
| 交付周期 | 未知（Q-07），但要求先跑通闭环 | USER_REQUIREMENT | → A |

**九项驱动因素中，八项指向 A，零项指向 B。**

## 3. Decision

> **DEC-01：采用模块化单体（Modular Monolith）+ 清晰限界上下文 + 可演进服务边界。**

- **Reason**：强一致不变量集中在「单据 ↔ 库存 ↔ 往来账」这条链上；在单进程单库内它们是一次本地事务，在微服务下需要 Saga/TCC + 对账。用分布式复杂度换取当前不存在的收益，是净损失。容量差两个数量级，不构成拆分理由。
- **Trade-off**：① 整体发布，单模块不能独立扩缩；② 模块边界只能靠**规则 + 架构测试**守住，靠人自觉必然腐化；③ 单点故障域。
- **对策**：ArchUnit 强制依赖方向与跨模块表访问禁令（Phase 0 落地，违反即构建失败）；每模块独立表前缀 + 独立 Flyway 迁移目录；跨模块只经应用服务或领域事件。
- **Rejected Options**：B（无驱动因素，且会把 INV-05/06/07 变成分布式问题）、C（无既有总线）、D 作为整体形态（会把强一致链路异步化，违背 INV-01）。

> **DEC-02：内部风格按上下文选择，不要求统一。**

| 上下文 | 风格 | 理由 |
|---|---|---|
| BC-3/4/5/6（Core） | **Hexagonal（Ports & Adapters）** | 领域规则需要与 MyBatis/外部系统隔离；未来抽服务时端口即边界 |
| BC-1/2/7/8（Supporting/Generic） | **Layered** | 以 CRUD + 少量不变量为主，六边形只会增加样板 |
| BC-9（Reporting） | 直接查询读模型 | 无领域层 |

> **DEC-03：局部采用事件驱动，不做全局 EDA。**
> 仅用于：① 过账 → 往来账生成；② 业务事件 → 单据关系图 / 审计；③ 审批完成 → 业务状态迁移；④ 业务事件 → 报表读模型。
> 其余交互（判权、主数据查询、库存预占与过账请求）是**同步进程内调用**，因为它们在同一用户操作的一致性范围内。
> 理由：提示词第十八章「不要所有操作都 MQ 化」。

## 4. 进程边界（当前与未来）

MVP 只有**一个可独立运行单元**：

```text
erp-app  :8500     — 全部 9 个上下文 + REST API
erp-console :8501  — 前端（Vite dev；生产由 erp-app 或静态服务托管）
```

不拆 `notify` / `file` / `job` 独立进程的理由：当前没有通知与文件的真实负载，定时任务只有 Outbox 投递与预占过期回收两个（单实例调度足够）。与 `oa-platform` 拆三个独立服务的差别在于：OA 的目标规模是万人级且有真实的推送与文件负载，本项目两者都没有（A-03/A-04）。

## 5. 防"为展示技术而拆服务"的检查项

进入 Phase 0 前写入工程基线，任一违反即 Gate 不通过：

1. 新增可部署单元必须先在 `ARCHITECTURE_EVOLUTION.md` 写出触发条件并被观测到；
2. 新增中间件必须通过 Complexity Budget（解决什么已存在的问题、简单方案为何不够、增加什么运维成本）；
3. ArchUnit 规则不得被 `@SuppressWarnings` 或例外清单绕过，例外必须写 ADR。
