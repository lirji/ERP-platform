# ADR-005 — P6 财务事件与信用权威查询

状态：实施决定，2026-09-22；范围为已批准 P6 MVP，不改变模块拆分或新增基础设施。

## 背景

P4/P5 的 v1 出入库事件实际只有单据关系字段，未携带财务金额/币种。直接要求 v1 必填金额会破坏历史重放。Sales 不能依赖 Finance 模块或直接查 fin_*，但 CONSISTENCY_MODEL §7 要求信用硬校验直接读财务权威数据。

## 决定

1. 新产生出入库事件使用 `PurchaseReceiptPosted.v2` / `ShipmentPosted.v2`，共享 DTO 为 kernel.events.PostedDocument；保留 v1 关系投影语义。财务消费者只消费完整 v2，不能为缺失载荷的历史 v1 猜金额。存量 v1 财务回填不自动执行。
2. 金额按每行累计数量乘单价 HALF_UP 四位的前后差值计算，再汇总本批金额；订单总额同样按行舍入后求和。采购/销售订单先加聚合行锁，避免并发分批拿到过期累计数量。零金额事实仍保留 AR/AP 以便追溯，零金额无需现金核销。
3. 本位币由主数据 CurrencyService 读取数据库唯一启用币种；缺失则业务事务失败。没有汇率或税额模型，不把未知数据默认为零税或某币种。
4. kernel 定义 SettledCreditQuery 端口，Finance 提供只读权威净核销查询。Sales 的实际信用占用为未取消订单累计本金减应收核销净额。核销立即释放可用信用，反核销立即恢复占用，无需等待事件投影。模块编译依赖仍通过原矩阵，数据所有权不变。
5. 财务与关系图消费者各自使用独立事务；失败向 Outbox 传播以重试。同批毒消息不使其他已成功消息回滚。消费者提交后但发布标记前崩溃，重放由来源唯一键/关系唯一键防重。
6. app 装配单线程固定延迟轮询，默认 1000ms（支持 100–60000ms），复用数据库 SKIP LOCKED 与既有批次/重试上限。测试默认关闭，OutboxLatencyIT 专门启用真实后台轮询。
7. `published_at` 使用 clock_timestamp()，避免以长事务开始时刻假装消息已完成；延迟测试测实际写入完成时间。

## 边界

本次不执行银行转账，收付款为业务凭证登记；不部署生产。业务日期暂沿用既有单时区约定。硬信用检查为 READ COMMITTED 决策时的权威财务视图；既有财务反核销可能使客户重新超限，后续订单会被拦截，不倒撤已经发生的销售。
